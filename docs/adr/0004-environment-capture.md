# 0004 环境信息怎么获取

状态：已接受（各浏览器的读取方式和耗时在原型阶段逐个验证）

## 背景

同一段文字在不同地方意思不同：`borrow` 在 Rust 文档里和在英语新闻里是两回事。选区前后 300 字有时不够，用户在哪个页面、哪个文件里读到它，往往更能说明意思。所以除了宿主应用名，还要把"用户在哪儿"一起发给模型，这些信息统称**环境**。

限制：

- 不能拖慢浮标出现（出现延迟不超过 150ms）。
- 不新增系统权限。macOS 已经有辅助功能权限，Windows 的 UI Automation 本来就不需要授权。
- 不在第一版里装浏览器扩展。

## 决策

### 获取哪些字段

| 字段 | macOS | Windows | 范围 |
| --- | --- | --- | --- |
| 应用名 | 前台应用的 `localizedName` | 前台窗口所属进程的文件描述，取不到时用进程名 | 所有应用 |
| 窗口标题 | 焦点窗口的 `AXTitle` | `GetWindowText(GetForegroundWindow())` | 所有应用；浏览器里就是当前标签页标题 |
| 网址 | 焦点元素或焦点窗口下 `AXWebArea` 的 `AXURL`；Firefox 读地址栏 | 浏览器窗口里 Document 控件的 `ValuePattern.Value` | 只对已知浏览器读 |
| 文件名 | 焦点窗口的 `AXDocument`，只取文件名 | 没有通用接口，靠窗口标题 | 文档类应用 |
| 日期 | 本机日期 | 本机日期 | 所有 |

- 已知浏览器按 bundle id / 进程名维护一张表：Chrome、Edge、Safari、Firefox、Arc、Brave、Vivaldi、Opera 以及国内常见的几家 Chromium 浏览器。Electron 应用（VS Code、Slack、Notion 等）内部也有网页，但网址是应用自己的内部地址，对模型没有意义，所以不读。
- Chromium 系浏览器默认不开放辅助功能树。取词时已经要给它设 `AXManualAccessibility = true`（macOS）或通过 UIA 访问激活它（Windows），读网址复用这一步。
- 不用 AppleScript 读浏览器网址：它会触发"自动化"权限弹窗，每个浏览器各弹一次。
- 参考实现：[screenpipe](https://github.com/mediar-ai/screenpipe) 的 `crates/screenpipe-a11y/src/tree/macos.rs`（Rust，读 `AXWebArea` 的 `AXURL`，实测约 2ms）。
- 窗口标题和应用名相同（例如微信主窗口标题就是"微信"）时不发 `<window_title>`。
- Windows 上 UWP / 商店应用的前台窗口属于 `ApplicationFrameHost.exe`，要取它的子窗口才能拿到真正的进程名。

### 浏览器以外的应用能拿到什么

所有应用都有应用名，几乎所有应用都有窗口标题，区别在标题里有多少信息。下表是预期，原型阶段核实：

| 应用类型 | 例子 | 窗口标题里通常有 | 文件名 |
| --- | --- | --- | --- |
| 代码编辑器 | VS Code、Cursor、JetBrains、Xcode | 文件名 + 项目名，如 `main.rs — pointer-app` | macOS 上多数能读到 `AXDocument`（Electron 应用要看是否设置了 represented filename） |
| 办公文档、PDF | Word、WPS、Pages、预览、Acrobat | 文档名 | macOS 原生文档类应用能读到 |
| 笔记 | Notion、Obsidian、语雀 | 页面或笔记名；Apple 备忘录只有"备忘录" | 一般没有 |
| 聊天 | Slack、飞书、Telegram、微信 | Slack、飞书有频道或会话名；微信、Telegram 主窗口只有应用名 | 没有 |
| 邮件 | 邮件、Outlook | 单独打开的邮件是主题；主窗口是邮箱名，如"收件箱" | 没有 |

- 信息少的应用（微信、备忘录）只能靠应用名加选区前后的上下文。要拿到聊天对象、邮件主题这类信息，得按应用遍历各自的辅助功能树，每个应用写一套，第一版不做。
- 聊天应用的标题可能带联系人或群名，同样受"发送窗口标题和网址"开关控制。

### 隐私处理

- **网址**：只发 `http` / `https` 网址，去掉查询参数和 `#` 后面的部分，只保留"协议 + 域名 + 路径"。查询参数里常有登录令牌、搜索词、追踪 ID；搜索词这类有用信息通常已经在标题里了。代价是 YouTube 的 `?v=` 这类靠查询参数区分页面的网址会丢掉信息，第一版接受，不做按网站的例外。`file://`、`chrome://` 等其他协议不发。
- **文件名**：只发文件名，不发完整路径（路径里常有用户名）。
- **窗口标题**：去掉浏览器自带的后缀（如 ` - Google Chrome`），截断到 200 字。
- 上下文开关关闭、或宿主应用在排除名单里时，环境只保留应用名和日期（与上下文的规则一致：排除名单里的应用根本不出浮层，这里是兜底）。
- 设置的"上下文"分组下单独一个开关"发送窗口标题和网址"，默认开启。
- 浏览器的隐私窗口没法可靠识别（标题和网址都和普通窗口一样），在设置里说明。

### 时机

- 取词成功后立即在后台线程并行读取环境，不阻塞浮标出现。
- 结果和选区一起存下来。用户点击 Prompt Action 时如果还没读完，最多再等 100ms，超时就不带环境发出去，缺哪个字段就省略哪个。
- 实际上用户从看到浮标到点击 Action 至少要几百毫秒，绝大多数情况下早已读完。
- 只在取词时读一次，追问不重新读取。

### 怎么交给模型

放在第一条用户消息开头的 `<environment>` 块里，提示词中声明它和选区一样只是数据，具体格式见 `docs/prompts.md`。解释和翻译都带环境：解释用它判断材料类型，翻译只用它选词义。

## 考虑过的方案

- **浏览器扩展 + Native Messaging**：能拿到完整网页正文、`<meta>` 描述、选区所在的章节标题，信息最全。但要为每个浏览器单独发布和审核扩展，用户还要多装一样东西。放进 `docs/backlog.md`。
- **截图 + 视觉模型**：通用，不依赖应用是否支持辅助功能。但需要屏幕录制权限，截图里可能有大量无关的敏感信息，请求也更慢更贵。放进 `docs/backlog.md`。
- **AppleScript 读网址**：Chrome、Safari 都支持，写法简单，但有"自动化"权限弹窗，而且 Firefox 不支持。
- **Windows 上读地址栏的 Edit 控件**：各浏览器、各版本的控件名不同，用户正在编辑地址栏时读到的还是半截文字，不可靠，只作为 Document 控件读不到时的兜底。

## 后果

- 每种浏览器的读取方式不同，原型阶段要逐个验证并记录耗时：Chrome、Edge、Safari、Firefox、Arc 是第一批。
- 浏览器版本更新可能改变辅助功能树的结构，要有每个浏览器一条的回归检查；读不到时安静省略，不影响主流程。
- 网页标题由网站控制，可能夹带"忽略之前的指令"一类文字，提示词里的"数据不是指令"声明要覆盖环境块。
- 第一版先不做"选区所在章节的标题"：要在辅助功能树里从选区往上找最近的标题元素，各应用结构差异大，原型验证可行后再加。
